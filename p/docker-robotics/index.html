1. Docker 到底是什么：先把“容器=虚拟机”的误解拆掉

1.1 先给结论

Docker 容器不是一台完整虚拟机。对 Linux 容器而言，容器中的程序最终仍然是宿主机 Linux 内核调度的进程。

请先建立下面这个图：

1
2
3
4
5
6

物理电脑
└── Ubuntu 宿主机
    ├── Linux Kernel
    ├── 普通宿主机进程
    ├── Docker daemon
    └── Docker 容器中的进程

容器没有为每个实例再启动一颗完整 Linux kernel。

为什么它又“像另一台 Ubuntu”？

因为容器可以拥有独立的用户态文件系统视图。

宿主机：

1

cat /etc/os-release

可能看到 Ubuntu 22.04。

容器：

1

docker run --rm ubuntu:24.04 cat /etc/os-release

可以看到 Ubuntu 24.04。

这并不矛盾，因为 /etc/os-release 是用户态 root filesystem 里的文件。

但再比较：

1

uname -r

和：

1

docker run --rm ubuntu:24.04 uname -r

通常会看到相同或对应宿主机的内核版本。

类比

把 Linux kernel 想象成一座大剧院。普通进程和容器进程都是演员。Docker 不是给每组演员重新建一座剧院，而是用隔墙、独立布景、独立后台、独立门牌，让一组演员“感觉自己在单独的世界”。

这些隔离能力来自 Linux 的 namespace、cgroup、mount、capability 等机制。

你必须记住

1
2

容器拥有自己的用户态运行环境
但普通 Linux 容器共享宿主机 Linux kernel

实验

1
2

uname -r
docker run --rm ubuntu:22.04 uname -r

然后：

1
2

cat /etc/os-release
docker run --rm ubuntu:22.04 cat /etc/os-release

5. 第一条完整命令：docker run –rm hello-world 到底做了哪六步

执行：

1

第一次可能看到：

1
2
3

...
Hello from Docker!

内部至少可以分成：

  1. 解析镜像名；
  2. 检查本地有没有镜像；
  3. 没有则从 registry pull；
  4. 根据 image 创建 container；
  5. 启动 container 主进程；
  6. 主进程结束，container 退出，--rm 再删除 container。

latest 是什么

没写 tag 时常解析成：

1

latest 只是一个 tag 名，不是“永远自动代表世界上最新版本”的神奇机制。

删除退出后的 container。

不会因为 --rm 自动删除 image。

验证：

1
2

docker ps -a

这里出现 Docker 最重要的生命周期规则

容器通常跟随它的主进程生命周期。

主进程退出，容器就变成 exited。

附录 A：104 个“为什么”——用问答把概念补到彻底理解

Q1. 为什么 docker ps 默认不显示停止的容器？

因为 docker ps 默认查询 running containers。停止后的 container object 仍存在，只是状态变成 Exited。用 docker ps -a 查看全部。

Q2. 为什么退出 bash 后容器停止？

如果你用 docker run -it ubuntu bash，bash 就是容器主进程。你执行 exit 后主进程结束，容器随之退出。

Q3. 为什么 Nginx 后台容器不会因为我关闭终端就停止？

因为 docker run -d nginx 后 Nginx 主进程仍在容器中运行，终端只是没有 attach 它。

Q4. 为什么 docker exec 要求容器正在运行？

exec 的意义是在现有 container namespace 里创建额外进程。容器不 running 时没有活跃运行环境可 exec。

Q5. 为什么 docker start 不需要再写 image？

container 在 create/run 时已经记录基于哪个 image、command、env、mount、network 等配置。start 只是重新启动这个现有对象。

Q6. 为什么反复 docker run ubuntu ... 会产生很多容器？

因为 run 的语义是创建新 container，而不是复用旧 container。临时实验常用 --rm 避免堆积。

Q7. --rm 会删除 image 吗？

不会。它只在 container 退出后删除 container object。

Q8. 为什么两个容器基于同一个 image，创建的文件却互不影响？

它们共享只读 image layers，但各自有独立 writable layer。

Q9. 为什么 bind mount 会让 image 里原目录内容看不见？

mount 会覆盖那个路径的当前 filesystem view。原 layer 内容没有删除，只是被挂载目录遮住。

Q10. 为什么修改 bind-mounted Python 源码一般不用 rebuild image？

运行时读取的是宿主机挂载文件，不是 image 里的静态 COPY。

Q11. 为什么修改 Dockerfile 后 docker restart 不够？

restart 只是重启旧 container。Dockerfile 变化需要重新 build image，并通常 recreate container。

Q12. 为什么 docker commit 不推荐作为正规环境维护方式？

虽然可以把当前 container 状态提交成 image，但手工历史难审计、难复现。Dockerfile 更适合作为可重复的环境定义。

Q13. 为什么 latest 不是严格版本锁？

latest 只是一个 tag，维护者可以让它指向不同 image。严格可复现应固定版本 tag，甚至 digest。

Q14. 为什么一个 image 可以很大？

基础镜像、apt 包、编译器、ROS、conda、缓存、COPY 的大文件和历史 layers 都会贡献体积。

Q15. 为什么在后续 layer 删除大文件，image 可能仍不显著变小？

大文件曾经进入前一 layer，后面的删除只是新 layer 中隐藏它，旧 layer 数据仍存在。

Q16. 为什么 multi-stage build 能减小 image？

最终 stage 只复制真正运行产物，不必携带 builder 中的编译器、源码和中间文件。

Q17. 为什么容器里的 localhost 通常不是宿主机？

因为默认 bridge container 有自己的 network namespace，127.0.0.1 指向当前 namespace 自己。

Q18. 为什么 -p 8080:80 左边是宿主机？

Docker CLI 的发布端口格式通常是 HOST:CONTAINER，因此 host 8080 转发到 container 80。

Q19. 为什么端口映射后仍访问不了应用？

可能应用没启动、没监听目标端口、只绑定 127.0.0.1、容器已退出或应用内部报错。

Q20. 为什么 host network 对 ROS 2 常更省事？

它减少 bridge/NAT 边界，DDS multicast 与动态 UDP 端口行为更接近宿主机原生运行。

Q21. 为什么 host network 不是永远更好？

它降低网络隔离，也更容易造成端口冲突和意外暴露。

Q22. 为什么同一 Compose 网络里 service 名常能解析？

用户定义 Docker network 带内置 DNS/service discovery，Compose 会为 service 提供网络别名。

Q23. 为什么 .env 变量不一定自动出现在容器里？

Compose .env 常用于 YAML 插值。只有 environment/env_file 等明确注入的变量才一定进入容器运行环境。

Q24. 为什么 docker compose config 特别重要？

它展示 Compose 变量插值、合并和解析后的最终配置，能排除“我以为 Docker 读的是这个值”的误判。

Q25. 为什么 docker logs 有时是空的？

Docker logs 主要收集 stdout/stderr。如果应用只写文件日志，需直接查看应用日志文件或挂载目录。

Q26. 为什么 docker inspect 比看 README 更能确认真实运行状态？

README 描述意图，inspect 展示容器创建后真实生效的 runtime configuration。

Q27. 为什么容器 root 创建的挂载文件在宿主机也是 root owner？

Bind mount 保留实际 Linux UID/GID 语义。容器 root 通常 UID 0，因此创建文件在宿主机也属于 UID 0。

Q28. 为什么 chmod 777 不是推荐的权限修复？

它过度放宽权限，并没有解决 UID/GID 映射问题。

Q29. 为什么 --privileged 能解决很多设备问题？

它开放大量 capability/device 权限，所以很多限制被一次性取消；也正因此风险较大。

Q30. 为什么 docker group 权限接近 root？

能控制 Docker daemon 的用户可以请求挂载宿主机敏感目录、启动高权限 container 等。

Q31. 为什么 Docker socket 很敏感？

/var/run/docker.sock 是控制 daemon 的 API 通道，容器一旦拿到它，可能间接获得高宿主机权限。

Q32. 为什么宿主机 nvidia-smi 正常不代表 container GPU 正常？

宿主机 driver 正常只是第一层；容器还需要 NVIDIA Container Toolkit/runtime 与 GPU request。

Q33. 为什么 container nvidia-smi 正常不代表 CUDA 一定正常？

nvidia-smi 主要验证设备和 utility 能力；CUDA 程序还需要匹配的用户态 runtime/toolkit。

Q34. 为什么 CUDA 正常不代表 OpenGL 正常？

compute 与 graphics 是不同 driver capability/用户态库链。

Q35. 为什么 OpenGL 正常也不代表窗口一定能显示？

还需要 X11/Wayland display server 地址、通信 socket 和认证。

Q36. 为什么只传 DISPLAY 不够？

DISPLAY 只是告诉程序目标显示地址；没有 socket/network 和授权，连接仍失败。

Q37. 为什么只挂 /tmp/.X11-unix 也不够？

程序仍需要正确 DISPLAY，而且 X server 可能需要认证许可。

Q38. 为什么 xhost + 不安全？

它过度放宽 X server 的客户端访问控制。

Q39. 为什么容器可以是 Ubuntu 24.04、宿主机是 22.04？

发行版用户态文件系统相互隔离，而 Linux 容器共享宿主机内核。

Q40. 为什么容器里 systemctl 常不可用？

很多应用容器没有完整 systemd 作为 PID 1，也没有完整 system bus/cgroup 环境。

Q41. 为什么有些开发容器又能运行 systemd？

可以专门配置 systemd 容器，但需要额外设置，不是普通 Docker 容器默认形态。

Q42. 为什么 apt install 在当前容器里成功，删容器后包没了？

安装修改写入容器 writable layer；container rm 后该层被删除。

Q43. 为什么一个好的开发容器应该允许删除重建？

可重建性意味着依赖被代码化记录，避免环境变成无法复制的“手工黑盒”。

Q44. 为什么 source code 最好留在 Git/宿主机，而不是只 COPY 进 image？

源码需要频繁编辑、版本控制和 diff；image 是构建产物，不是源码管理系统。

Q45. 为什么 ROS workspace 经常 bind mount？

宿主机负责编辑和 Git，容器提供 ROS/编译依赖，双方通过同一源码目录协作。

Q46. 为什么整个 workspace mount 与只 mount src 的结果不同？

如果 mount 整个 workspace，build/install/log 也可能写回宿主机；只 mount src 时构建产物可能留在容器或 volume。

Q47. 为什么 source /opt/ros/.../setup.bash 新 shell 可能要重新执行？

source 只修改当前 shell 环境。新 shell 是否自动加载取决于 entrypoint/bashrc 等项目设置。

Q48. 为什么 ROS image 常有 entrypoint？

entrypoint 可统一 source ROS 环境、设置变量，再执行用户 command。

Q49. 为什么排错时不能随便覆盖 entrypoint？

--entrypoint bash 可能绕过项目初始化步骤，导致 ROS 环境等未配置。

Q50. 为什么 Docker image 也区分 amd64/arm64？

容器程序仍运行真实 CPU 指令，不同架构需要匹配的可执行文件/image 或模拟层。

Q51. 为什么 x86 仿真容器不一定原样搬到 ARM 机器人？

除了 image architecture，还涉及设备、driver、kernel、性能和硬件接口差异。

Q52. 为什么 Docker 对仿真到真机迁移仍然有价值？

用户态依赖、构建流程和应用结构可以标准化，但硬件相关部分仍需适配。

Q53. 为什么 build cache 会占大量空间？

BuildKit 保存可复用中间结果以加快后续构建，长期多项目使用会积累。

Q54. 为什么 prune cache 后下一次 build 变慢？

缓存被删除，昂贵的构建步骤必须重新执行。

Q55. 为什么 volume prune 要最谨慎？

volume 常保存真正持久业务/实验数据，而 image/container 往往可重建。

Q56. 为什么不能直接删除 /var/lib/docker 里的某个 layer？

Docker metadata 和 snapshot 由 daemon 管理，手工修改可能造成内部状态损坏。

Q57. 为什么 container log 能写满磁盘？

stdout/stderr 可能被 logging driver 持久保存，若应用高频输出且无 rotation 会持续增长。

Q58. 为什么 docker compose down 通常不删除 image？

down 主要清运行时 project 对象，保留 image 便于下次快速启动。

Q59. 为什么 docker compose down -v 风险更高？

-v 会删除 Compose 相关 volume，持久数据可能丢失。

Q60. 为什么 docker compose up -d --build 常见？

它在需要时先构建 image，再根据新 image/config 创建或更新 service container，并后台运行。

Q61. 为什么改 mount 后 restart 可能没用？

mount 属于 container creation 配置，通常需要 recreate container。

Q62. 为什么改 Dockerfile 和改 ROS 源码是两种 build？

Docker build 构建运行环境 image；colcon build 编译 ROS packages。两个 build 层级完全不同。

Q63. 为什么修改 Python 源码不一定需要 colcon build？

取决于 ROS package 安装方式和 Python packaging；symlink-install 等模式可以让源码变化直接反映，但具体项目需看 package。

Q64. 为什么修改 C++ ROS 节点通常需要 colcon build？

C++ 源码需要编译和链接生成可执行文件/库。

Q65. 为什么 docker context 值可能造成 CLI 连接错 daemon？

Docker CLI 可以配置多个 context，当前 context 可能指向本地或远程 Docker endpoint。

Q66. 为什么 sudo docker 和普通 docker 行为偶尔不同？

HOME、config、credential store、context、environment 和权限都可能不同。

Q67. 为什么 newgrp docker 只对当前会话有意义？

它创建带新 group membership 的 shell；正式重新登录后 group membership 会自然刷新。

Q68. 为什么陌生 image 不能因为“来自 Docker Hub”就默认可信？

Docker Hub 既有官方镜像也有任意第三方上传，需检查发布者、源码、tag 和更新情况。

Q69. 为什么 .dockerignore 也属于安全配置？

它可以防止 SSH key、.git、secret、数据集等被意外发送到 build context 或 COPY 进 image。

Q70. 为什么 Dockerfile 不应该硬编码 token/password？

镜像历史、layer 和 registry 可能泄露 secret，应使用合适 secret 机制或 runtime configuration。

Q71. 为什么 Docker 不是“绝对安全沙箱”？

容器共享 host kernel，隔离强度取决于 kernel、runtime、capability、mount、seccomp、配置和漏洞。

Q72. 为什么机器人 Docker 更要重视安全？

机器人常需要设备、host network、GPU、X11 等更高 host 接触面。

Q73. 为什么 headless 仿真不等于不需要 GPU？

不显示窗口只是取消本地 display，离屏渲染或计算仍可能使用 GPU。

Q74. 为什么 headless 模式通常不需要 X11？

如果程序完全不创建桌面显示窗口，就不需要连接 host X server。

Q75. 为什么 MuJoCo GUI 配置比普通 CLI 容器复杂？

它同时跨越 filesystem、GPU device、graphics library、display server、socket 和权限多个层次。

Q76. 为什么 Docker Desktop 教程和 Ubuntu 原生 Docker Engine 有区别？

Desktop 产品在某些平台有额外 VM/GUI/集成层，而 Ubuntu 原生 Engine 直接使用 Linux host kernel。

Q77. 为什么你当前机器人项目更适合先学原生 Docker Engine？

因为 GPU、X11、device、ROS networking 都直接发生在 Linux 上，理解底层更重要。

Q78. 为什么不建议现在先学 Kubernetes？

你当前任务是单机机器人开发。若基本 image/container/mount/network/GPU 未掌握，再叠加集群编排只会增加抽象。

Q79. 为什么 Compose 不等于 Kubernetes？

Compose 主要声明和管理单机的一组 containers；Kubernetes 是面向集群的调度、控制、服务发现和编排系统。

Q80. 为什么 wrapper script 不是坏东西？

项目脚本可统一 GPU/X11/env/Compose 操作，降低日常复杂度。关键是你需要能理解并排查其底层。

Q81. 为什么学会底层 Docker 后仍建议优先按项目 manage.sh 使用？

作者脚本可能包含项目特定初始化和兼容逻辑。理解底层是为了排错和修改，不是为了无理由绕过标准入口。

Q82. 为什么 docker inspect 能帮助看懂 manage.sh？

脚本无论如何包装，最终创建的 container runtime config 都会反映在 inspect 中。

Q83. 为什么项目脚本里会先处理 xhost 再 compose up？

GUI 容器启动前需要确保 host X server 接受对应客户端连接。

Q84. 为什么 .env.example 通常不直接被项目长期使用？

它是配置模板，用户复制成 .env 后进行本地定制，同时 .env 常不提交敏感/机器特定内容。

Q85. 为什么 .env 不应该随便提交 token？

Git 历史会永久记录 secret，一旦提交即使删除也可能仍存在历史中。

Q86. 为什么 Docker 环境和宿主机 ROS 环境不要混着 source？

容器有自己的 root filesystem 和环境。宿主机 source 不会自动“穿透”到 container shell。

Q87. 为什么容器内 echo $ROS_DISTRO 与宿主机可以不同？

环境变量属于各自进程环境，且两边安装了不同 ROS 用户态。

Q88. 为什么 ROS 节点能否通信与两边 distro 名字不同不是简单一一对应？

通信涉及 DDS wire compatibility、message definitions、middleware、QoS 等，不能只看环境变量。

Q89. 为什么 Docker 的价值在机器人里不仅是“装依赖”？

它还规范网络、device、GPU、GUI、用户、工作目录、启动入口和部署流程。

Q90. 为什么一个项目的 Compose 文件也相当于部分系统架构文档？

它直接描述有哪些 services、网络关系、mount、依赖和运行入口。

Q91. 为什么调试 Docker 时不应该从最上层算法开始？

底层 container/GPU/network 若未正常，上层算法现象会被误判。

Q92. 为什么故障排查应该从 Host → Docker → Container → GPU/X11 → ROS → App？

这是从基础依赖到上层应用的因果顺序，能最快缩小错误范围。

Q93. 为什么“重装 Docker”通常不应该是第一反应？

多数问题属于权限、container config、mount、network、GPU runtime、应用日志等，重装不仅无效还可能破坏已工作环境。

Q94. 为什么一个容器 Exited 不等于 Docker daemon 坏了？

它更常意味着容器主进程正常结束或异常退出。先看 logs 和 ExitCode。

Q95. 为什么 ExitCode=0 仍可能“看起来失败”？

0 表示进程认为自己正常结束，但你可能期待它长期运行。问题可能是 command 设计而非 crash。

Q96. 为什么 OOMKilled 是一个重要 inspect 字段？

它告诉你容器是否因内存不足被内核 OOM killer 终止。

Q97. 为什么 /dev/shm 太小会让某些程序奇怪崩溃？

共享内存不足会影响使用 POSIX shared memory 的图形、浏览器、ML/IPC 程序。

Q98. 为什么 Docker 的 CPU 限制并不是给容器“分配真实独占 CPU”这么简单？

cgroup 可以限制 CPU quota、shares、cpuset 等资源调度行为，语义比简单“给四核”更丰富。

Q99. 为什么 Docker volume 的真实目录不建议日常手工编辑？

Docker 负责管理 volume 生命周期和路径；应用级修改最好通过挂载后的容器路径或正规备份流程。

Q100. 为什么备份数据库 volume 不能只在数据库高速写入时随便 tar？

文件系统级复制未必得到应用一致性快照，数据库应结合自身 dump/snapshot/停写机制。

Q101. 为什么 docker save 比 docker export 更适合移动一个构建好的 image？

save/load 保留 image layers、tags 等镜像信息；export 主要导出单个 container rootfs。

Q102. 为什么 Git commit 和 Docker image tag 应该建立对应关系？

这样可追踪某个运行 image 来自哪一版源码，便于复现实验。

Q103. 为什么最终应让实验结果输出到宿主机挂载目录？

这样 container 即使删除，论文图表、日志和结果仍由宿主机文件系统管理和备份。

Q104. 为什么 Docker 的最终熟练标准不是背命令？

真正熟练是看到任何复杂命令都能拆成 lifecycle、filesystem、network、environment、device、resource、security 七个维度。

不要把它当成一条“巨长神秘命令”。

把它拆成七类：

第一类：生命周期

1

docker run

创建并启动新 container。

1

--rm

container 主进程退出后删除 container object。

第二类：交互

1

-it

让 stdin + pseudo-TTY 支持交互 shell。

第三类：对象名称

1

--name robot_dev

让 Docker 对象有一个可读名称。

第四类：网络

1

--network host

直接使用 host network namespace。

第五类：GPU 和 GUI

1

--gpus all

请求全部 NVIDIA GPU。

1

-e DISPLAY="$DISPLAY"

把 host DISPLAY 地址注入 container。

1

-v /tmp/.X11-unix:/tmp/.X11-unix

让 container 看到 host X11 Unix socket。

第六类：ROS 与源码

1

-e ROS_DOMAIN_ID=0

注入 ROS 2 runtime environment。

1

-v "$PWD/workspace:/root/workspace"

把源码 workspace bind mount 进 container。

第七类：资源与启动命令

1

--shm-size=2g

设置容器共享内存大小。

1

robot-image:dev

指定 image。

1
