G1 仿真（三）：用 Docker 启动 MuJoCo

区分宿主机和 Jazzy 容器，完成依赖导入、编译、启动与仿真检查。

2025-07-04
阅读时长: 3 分钟

本文使用 maxwellrobotics/g1-ros2，目标是完成一次可检查的 MuJoCo 仿真启动。后续建图、导航和自定义算法见 G1 导航进阶。

1. 先确认项目版本

核对日期：2026-09-17。项目主分支使用 Ubuntu 24.04 + ROS 2 Jazzy 开发容器，早期 Humble 路线位于 humble-unitree 分支。本文按主分支组织，不要把旧分支的启动说明与新分支的包混用。环境依据见项目 README。

宿主机负责 Docker、NVIDIA 驱动和显示服务；容器负责 ROS 与工作空间。宿主机装有 Humble，不表示容器也应 source Humble。进入容器后通过 echo "$ROS_DISTRO" 检查实际环境。

2. 检查宿主机

在宿主机终端执行：

1
2
3
4
5
6

lsb_release -a
docker version
docker compose version
git --version
nvidia-smi
printf '%s\n' "$XDG_SESSION_TYPE" "$DISPLAY"

检查 Docker 客户端与服务端是否都能连接，Compose 是否可用，宿主机 GPU 是否正常。图形模式按项目要求使用 X11 会话；仅设置 DISPLAY 不能替代有效的显示授权。

没有 Docker 时按 Docker Engine 的 Ubuntu 安装说明 安装；容器 GPU 还需要 NVIDIA Container Toolkit。先完成 Docker 基础教程 中的 GPU 与显示检查，再进行项目构建。

3. 下载项目并导入依赖

以下命令在宿主机执行，新建工作目录：

1
2
3
4
5
6
7

mkdir -p ~/workspaces
cd ~/workspaces
git clone https://github.com/maxwellrobotics/g1-ros2.git
cd g1-ros2
git rev-parse HEAD
sudo apt update
sudo apt install python3-vcstool

记录提交号，之后可以对照同一份 README 和配置复现。vcstool 提供 vcs 命令，根据仓库的 workspace.repos 下载依赖项目。

首次配置时复制环境模板，再导入依赖：

1
2

cp .env.example .env
./scripts/import-externals.sh

已有 .env 时先对比模板，不要覆盖自己的配置。检查导入日志中是否有失败项，并确认 workspace/src 中出现依赖包。依赖没下载全时，不要继续靠反复编译解决。

4. 启动与进入容器

仍在宿主机的仓库根目录：

1
2
3

docker compose config
./scripts/manage.sh start
./scripts/manage.sh exec

docker compose config 用于检查配置能否解析；start 与 exec 的具体行为由项目脚本封装。进入容器后执行：

1
2
3

echo "$ROS_DISTRO"
pwd
ls /root/workspace

本文对应的主分支应显示 jazzy，工作空间位于 /root/workspace。容器中的路径与宿主机 ~/workspaces/g1-ros2 不相同，它们通过 Compose 中的挂载关系连接。

5. 编译并加载工作空间

下面在容器内执行：

1
2
3
4

cd /root/workspace
colcon build --symlink-install --cmake-args -DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
source install/setup.bash
ros2 pkg prefix g1_bringup

src 是源码，build 是构建中间文件，install 是 ROS 查找包时使用的安装结果，log 保存编译日志。每个新终端都需要加载相应环境；一次 source 不会自动改变其他已打开的终端。

编译失败时，找到第一个失败包与该包最早的错误。区分依赖缺失、源码版本不匹配和编译资源不足，再决定是否重建。最后的汇总行只说明失败结果，通常不是根因。

6. 启动 MuJoCo

在已加载工作空间的容器终端执行：

1

ros2 launch g1_bringup bringup.launch.py headless:=false

应看到 MuJoCo 场景和机器人，终端持续运行且没有反复退出的关键节点。模型出现在窗口中只是第一项检查，还要观察物理仿真是否持续推进、机器人是否稳定。

新开宿主机终端，进入同一容器后检查 ROS 图：

1
2

cd ~/workspaces/g1-ros2
./scripts/manage.sh exec

进入容器后：

1
2
3
4
5

cd /root/workspace
source install/setup.bash
ros2 node list
ros2 topic list -t
ros2 control list_controllers

保存节点、话题与控制器状态，作为后续修改场景和算法前的基线。

7. 判断问题发生在哪一层

现象检查顺序
Docker 连不上服务状态、当前用户权限、Docker context
导入依赖失败网络、vcs 是否安装、workspace.repos 与分支
容器启动失败Compose 配置、GPU 运行时、挂载路径、日志
找不到 g1_bringup编译是否成功、是否 source 当前工作空间
MuJoCo 没有窗口X11 会话、DISPLAY、显示授权与图形驱动
窗口有模型但机器人不稳定控制器状态、策略文件、模型与关节配置
有话题但看不到消息发布者、消息类型、QoS、DDS 配置

排错时先确认下层正常，再检查上层算法。

8. 本阶段完成标准

  • 宿主机能够启动并进入项目容器。
  • 容器发行版与当前项目分支一致。
  • 工作空间编译成功，能够找到 g1_bringup。
  • MuJoCo 正常运行，控制器状态可查看。
  • 能区分宿主机命令、容器命令和 ROS 工作空间路径。

完成后阅读 G1 导航与自定义算法，按遥控、反馈、建图、定位、导航的顺序继续。
